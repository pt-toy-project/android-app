# 로컬 저장 구조

## v3.0 / DB v2

아래 v1 설명은 이전 구조의 기록입니다. 현재 새 설치는 `schema_v2.sql`, 기존 설치는 `migration_1_2.sql`로 v1→v2를 실행합니다. Android SQLiteOpenHelper의 업그레이드 트랜잭션 안에서 source 컬럼과 인덱스만 변경합니다. 기존 행은 모두 PERSONAL입니다. 삭제나 PK 재발급은 하지 않습니다. 새 설치 SQL도 원본 v1 SQL에 같은 마이그레이션을 적용하므로 sqlite_master 구조가 동일합니다.

활성 인물·템플릿·출처가 UNIQUE이며 PERSONAL과 HERO_DAY를 별도 채택할 수 있습니다. 완료 기록의 인물·템플릿·날짜 UNIQUE는 변경하지 않아 두 출처에서 같은 날 이중 코인을 받지 않습니다. 오늘은 HERO_DAY, 나만의 계획은 PERSONAL만 조회합니다. 편집에서 출처·인물·템플릿을 변경할 수 없습니다.

startHeroDay는 여덟 블록 생성과 선택 인물 변경을 같은 트랜잭션에서 처리합니다. 기존 채택은 ID만 반환하여 사용자 시각·반복·활성화·알림 설정을 보존합니다. 일부 블록 실패는 새 행과 선택 변경을 모두 롤백합니다. 삭제한 블록의 재시작은 기존 규칙대로 새 ID를 생성하되 완료 보상은 이전 기록으로 보호합니다.

계측 asset `historical_routines_v1.db`는 실제 원본 v1 SQL로 생성한 SQLite 파일이며 user_version=1입니다. 사용자 제목·ID 41·완료 제목 스냅샷·잔액 80·보유/적용 칭호·이전 기록·선택 인물을 포함합니다. 사용자 실기기에서 추출한 데이터는 아닙니다. 호스트는 파일 업그레이드 전후 모든 기존 컬럼과 새 설치 구조를 비교합니다. 계측 테스트는 같은 파일로 SQLiteOpenHelper 업그레이드를 검증하도록 작성했으나 기기 실행은 별도입니다. 기존 설정 preferences 이름과 키는 변경하지 않습니다.


앱은 백엔드 없이 기기의 Android `SQLiteOpenHelper` 데이터베이스
`historical_routines.db`를 사용한다. 스키마 버전은 1이며 설치 기기의 Android가 제공하는
SQLite 엔진을 사용하므로 SQLite 버전은 기기에 따라 달라진다. 실제 스키마는
`app/src/main/assets/database/schema_v1.sql`에 있다. 다음 스키마 버전이 추가될 때는
`onUpgrade`에 데이터를 보존하는 명시적 마이그레이션을 추가해야 한다. 버전이 맞지 않으면
현재 구현은 삭제하거나 재생성하지 않고 실패한다.

| 테이블 | 용도와 보호 장치 |
| --- | --- |
| `user_routines` | 인물·템플릿 ID, 도입 당시 제목, 사용자 시간/요일/활성화/알림 상태. 증가하는 정수 PK와 삭제하지 않은 인물·템플릿 쌍의 UNIQUE 인덱스 |
| `completion_records` | 루틴 FK, 현지 날짜, 인물·템플릿 ID, 완료 당시 제목 스냅샷, 지급 코인. 루틴·날짜 복합 PK와 인물·템플릿·날짜 UNIQUE로 재도입 후에도 중복 보상 방지 |
| `wallet` | 하나의 정수 잔액. 음수 및 SQLite REAL 변환을 CHECK로 거절 |
| `owned_items` | 아이템별 한 번만 구매하는 PK, 당시 가격과 구매 시각 |
| `applied_item` | 실제 보유 아이템만 적용하도록 FK, 하나의 적용 상태 |
| `legacy_completions` | 기존 샘플 기록을 별도 보관. 새로운 역사 루틴 ID와 연결하지 않음 |
| `app_metadata` | 선택 인물과 원자적인 이전 완료 표시 |

외래 키는 연결을 열 때마다 활성화한다. 기록이 있는 루틴은 물리 삭제할 수 없으며 UI의
삭제는 비활성화와 삭제 표시만 수행한다. 다시 같은 템플릿을 추가하면 새로운 ID를 사용한다.
현재 활성 템플릿을 다시 추가하면 기존 ID를 반환하며 사용자가 수정한 시간과 요일은 유지한다.
기록 목록은 기본 100개, 최대 500개씩 읽고 오프셋을 지원한다. 날짜 및 인물·날짜 인덱스를
사용하며 날짜별 루틴 조회는 행마다 완료 여부를 조회하는 N+1 패턴을 피한다.

## 날짜와 보상 규칙

실천 날짜는 타임존 오프셋 없는 `YYYY-MM-DD` 현지 달력 날짜다. 시간은 사용자 기기의
현지 `HH:mm`, 요일은 월요일부터 일요일까지 7비트 정수다. 알림 예약에서 현재 타임존과
DST를 적용한다. 기록 날짜를 다른 타임존으로 이동시키지 않는다.

루틴을 추가한 현지 날짜부터, 선택된 요일에 한해 오늘 또는 과거의 실천을 기록할 수 있다.
도입 이전이나 미래 날짜에는 보상을 지급하지 않는다. 완료 한 번에 10코인을 지급하며
완료 기록 INSERT와 잔액 증가를 같은 트랜잭션에서 처리한다. 이미 기록된 루틴·날짜는
추가 지급하지 않는다. 정수 최댓값에서 10을 안전하게 더할 수 없으면 기록과 잔액을 모두
변경하지 않는다. 과거 제목과 인물은 완료 기록의 스냅샷에서 읽는다.
같은 인물의 같은 습관을 완료한 뒤 삭제하고 다시 추가해도 해당 날짜는 완료 상태로
표시하며 보상을 다시 지급하지 않는다. 새 도입 ID는 따로 유지하고 과거 기록의 원래 ID와
제목을 변경하지 않는다. 다음 실천 날짜에는 새 도입으로 정상 기록할 수 있다.

구매도 잔액 확인, 조건부 차감, 보유 항목 INSERT를 하나의 트랜잭션에서 처리한다.
중복 구매나 잔액 부족은 상태를 변경하지 않는다. INSERT 실패가 발생하면 차감이나 보상
증가도 롤백한다. 코인은 현금 가치가 없는 로컬 포인트다. 클라이언트의 시간·저장소 변조를
통제하는 서버나 보안 원장은 구현하지 않았다.

## 기존 데이터 이전

처음 저장소를 열 때 `routine_state_v1`의 `selected_hero`와
`completed:인물ID:YYYY-MM-DD` 기록을 트랜잭션으로 가져온다. 이전 완료 표시도 같은
트랜잭션에서 저장한다. 이미 이전한 경우 반복 실행하지 않는다. 기존 SharedPreferences
파일은 삭제하거나 변경하지 않는다. 해석할 수 없는 잘못된 값도 원본 파일에 그대로 남는다.
기존 `app_settings`는 기존 이름과 키로 계속 사용한다.

옛 1~6번 샘플 루틴이 실제 역사 자료와 다른 내용을 의미하므로 이전 기록은 별도 목록에
보존하고 새 루틴 완료로 간주하지 않는다. 이전 기록에 코인을 소급 지급하지 않는다.
인물별 기록 화면은 이전 샘플 기록의 목록과 개수도 같은 인물 ID로 필터링한다.

## 문자열과 메모리

문자열은 SQLite `TEXT`이며 제한은 Kotlin 검증과 SQL `CHECK`로 명시한다.
SQLite의 `VARCHAR(n)`이나 `CHAR(n)` 선언이 길이나 고정 패딩을 보장한다고 가정하지 않는다.
한글·이모지는 UTF-8 저장 바이트 수, Unicode 문자 수, Kotlin UTF-16 코드 단위 수가 다르다.
UI 입력 길이는 Kotlin 코드 단위 기준으로 더 엄격히 검증하며 문자열을 잘라 저장하지 않는다.
제목은 최대 160 코드 단위, ID는 허용된 ASCII 문자와 길이로 제한한다.

잔액과 가격은 부호 있는 64비트 정수이며 소수나 문자열로 저장하지 않는다. SQL의 정수
넘침이 REAL로 변환되면 CHECK가 거절하고, 정상 경로는 그 전에 조건부 UPDATE로 차단한다.
메인 스레드에서 파일·DB 작업을 수행하지 않도록 호출자가 `AppIo`에서 저장소를 생성하고
사용·닫는다. Cursor와 SQLiteStatement도 사용 후 닫는다. TEXT나 인덱스 변경만으로 앱 RAM
절감량을 주장하지 않는다. 디스크, DB 캐시, Kotlin 객체, 이미지 디코딩 메모리는 다른
측정 대상이며 현재 프로파일링한 메모리 수치는 없다.

## 검증

`RoutineRulesTest`는 날짜·요일·입력·정수 경계·보상·구매의 순수 규칙을 JVM에서 검증한다.
`python3 scripts/verify_database.py`는 동일한 SQL asset을 사용해 실제 호스트 SQLite의
제약조건, 외래 키, 인덱스, 롤백, 여러 연결의 중복 완료 방지를 검증한다. 이 검증은 Android
저장소 메서드 실행을 대신하지 않는다.

`AppRepositoryTest`는 격리된 임시 Android DB와 임시 preferences로 실제 이전, 보상,
구매, 동시 요청, 제목 보존, 중복 추가, 오버플로, 실패 주입 롤백, 페이지 제한을 검증한다.
이 기기 테스트는 연결된 Android 기기에서 실행해야 하며 APK가 빌드되었다는 이유로 통과로
기록하지 않는다.
